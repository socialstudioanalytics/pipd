Pali
Answers.

A verbatim-retrieval answering tool that meets the most common talking points used to deny, distort, or relativise the Palestinian condition. Two doors, four routes, one corpus: a search bot that recognises questions, keywords, and out-of-scope queries — and a themed catalog of 13 myth categories. §01 — Concept

The information environment is asymmetric. The tool corrects a small part of that.

Pali Answers does not try to "win arguments," does not "explain in its own words," and does not generate new content on the fly. It surfaces a curated, sourced corpus — verbatim — to ordinary users encountering common talking points. The architecture is built around not rewriting the editorial team's work.

Problem 01

Talking points outrun corrections.

The same dozen claims circulate everywhere — "Israel left Gaza in 2005", "Hamas = ISIS", "from the river to the sea is genocidal". Each takes seconds to deploy and hours to refute properly.

Problem 02

General-purpose AI hedges.

Mainstream chatbots tend to launder these claims as "complex" or "two-sided." They rarely point users to UN, ICJ, B'Tselem, HRW, Amnesty, or Adalah primary sources.

Problem 03

Even retrieval bots quietly rewrite.

Most chatbot platforms — even "RAG-based" ones — silently summarise, merge, or paraphrase the retrieved content. The output drifts from what the editorial team wrote. Pali Answers fixes the failure mode at the architecture level: no LLM in the output path.

§02 — Dual system

Two doors. Four routes. One corpus.

The search bot is not one path but four — a classifier routes the user's input to the correct destination. The browse catalog is its own self-contained discovery surface. All five end-states render content that is either verbatim from the corpus or a fixed canned response. Nothing is generated on the fly.

◆ Door A · Search bot

The bot that classifies.

Routing only · LLM as classifier, never as writer

A single input field. The classifier decides what the user typed — a full question, a keyword, a knowledge query, or an unrecognised myth — and routes accordingly. The output is always verbatim corpus content or a fixed canned response.

Route 1 · Question
Full-sentence input matching a known myth. "did israel leave gaza in 2005" → embed → match Q3 → render canonical answer verbatim, all angles, all citations, fixed template header.
Route 2 · Keyword
Short input (1–2 words). "aid" → suggestion dropdown of up to 5 related myths with semantic match (so "elections" surfaces voting + Hamas Qs) → user taps one → verbatim answer renders.
Route 3 · Knowledge query · PIPD Scenario A
"what is Hamas", "what happened in 1948" → fixed canned response: "Pali Answers is not a general knowledge tool" + curated external links to communicatingpalestine.org and thepipd.com.
Route 4 · Unknown myth · PIPD Scenario B
Assertive claim with no corpus match ("Palestinians sold their land") → fixed canned response: "This myth is not yet in our database" + curated links to decolonizepalestine.com and thepipd.com myths page.
LLM usage
A single ~50-token classification call. cheap No generation in any output path. The bytes the user sees are either the editor's bytes or a fixed template string.
Guarantee
By architecture. The LLM is structurally incapable of inventing a claim, paraphrasing an answer, or merging two myths — because it is never asked to generate output text.

§03 — Methodology

One classifier. Five end-states.

The LLM does exactly one thing: read the user's input and decide which of four search routes it belongs to (or detect that the user tapped a theme instead). Everything downstream is deterministic — verbatim corpus content or one of two fixed canned-response templates. No output is generated at runtime.

Note 01 — The LLM is a classifier, not a writer

One model call. ~50 output tokens.

The classifier receives the user's input and outputs one of four labels: QUESTION, KEYWORD, KNOWLEDGE_QUERY, or UNKNOWN_MYTH. It is never asked to produce, summarise, or rewrite any answer content. Everything downstream is deterministic Python/JS code with no model in the loop.

Note 02 — Verbatim with a fixed template header

The user sees exactly what the editor wrote.

For Routes 1 and 2, the matched canonical answer renders verbatim, preceded by a fixed template: "Answer for: <canonical Q title>". Four answer angles appear by default in editorial order; a "see more" control reveals the rest. Citations and Read More sections are preserved byte-for-byte from the corpus.

Note 03 — Two canned responses, never confused

Knowledge ≠ unknown myth.

Route 3 fires when the input is an interrogative knowledge query ("what is Hamas", "what happened in 1948") — sends users to communicatingpalestine.org external resources. Route 4 fires when the input is an assertive claim with no corpus match ("Palestinians sold their land") — sends users to decolonizepalestine.com myths page. The classifier distinguishes interrogative + topical from declarative + accusatory.

Note 04 — Why the theme browser exists at all

Discovery is not a search problem.

If a user doesn't know that a particular myth exists, they can't search for it. The theme browser is the answer to that: 13 cards on the home page, each opening to an accordion of myths within that theme. Tapping a myth expands it inline to reveal Answer 1, Answer 2, Answer 3, Answer 4, with Read more for the rest. No LLM at any point in this lane.

§04 — Theme hierarchy

What the catalog looks like.

13 themes on the home page as clickable cards. Tap one to open its theme page, where the myths within are listed as an accordion. Tap a myth to expand it inline and read the first four answer angles; "Read more" expands the rest. No language model is invoked anywhere in this lane.

The 13 themes are drawn from the corpus's own editorial categories, with two adjustments: a few topical themes are kept distinct because they are how users actually arrive (Aid & Famine, Antisemitism Accusations), and a few categories are paired where one is too small to stand alone (Apartheid + Democracy, Refugees + Right of Return). The result is a taxonomy close to how the corpus already organises itself, not an editorial overlay.

A single myth can sit in more than one theme. The interactive mock below behaves the way the production app will: tap a card to drill in, tap a myth to read it.

§07 — Cost model

The classifier-only collapse.

Once the LLM is reduced to a ~50-token classifier and removed from every output path, model inference becomes a rounding error inside a rounding error. At 5–10K sessions/month, the dominant cost is the platform fees of whichever vendor wraps the search backend — not tokens. Hosting the catalog itself is free because it ships as a subpage of the parent CMS.

Per-session cost. Routes 1 & 2 (question / keyword → verbatim corpus) trigger one classifier call plus one embedding call plus one vector-store read — about $0.0002 / session. Routes 3 & 4 (knowledge query / unknown myth → canned response) skip retrieval entirely — about $0.0001 / session. Browse sessions cost $0.00000 (pure JSON lookup from CDN). PIPD's "Scenario A" maps to Route 3; "Scenario B" maps to Route 4.

Per-month cost. Across 5,000–10,000 sessions at a 55% search · 45% browse mix, the total LLM bill is approximately $0.30 – $1.00 per month. The dominant line items are the platform/hosting fees of whichever vendor runs the search backend, not model usage.

§08 — Assumptions · Risks · Roadmap

What could go wrong, and what comes next.

The verbatim-retrieval design removes the worst risks of v0.2 (LLM rewriting drift, generated misattributions) but introduces one important new one: the classifier must correctly distinguish the four routes — and especially must not confuse Scenario A (knowledge query) with Scenario B (unknown myth). Each risk below has a mitigation tied to a build artefact, not a process.

Risk · classifier accuracy

The four-way routing decision is the whole system.

The classifier has to distinguish QUESTION from KEYWORD from KNOWLEDGE_QUERY from UNKNOWN_MYTH. A misroute is the only way a user can land on a wrong answer. Mitigation: a hand-built eval set of ~50 examples per route (200 total), enforced as a CI check on any prompt change. Target ≥95% top-1 accuracy on the eval. Confidence floor at 0.62 → otherwise default to UNKNOWN_MYTH (the safest failure mode).

Assumption · the mix holds

Browse absorbs 40–60% of traffic.

If the home screen prioritises the search input and buries the theme cards, the search lane bears most of the volume. The cost picture barely changes (LLM use is already negligible) but the discovery surface goes underused. Mitigation: design audit at launch; 13 theme cards above the fold on the home page; analytics on browse-vs-search split per surface.

Risk · editorial drift

An answer becomes outdated and no one notices.

Every entry has a last_reviewed field; entries older than 6 months surface in the editorial backlog automatically. Death tolls, ICJ proceedings, and policy changes have explicit watch lists. Both surfaces deploy from the same commit, so a single edit updates both lanes.

Risk · taxonomy drift

The 13 themes stop matching the corpus.

As new myths are added, the theme mapping must be reviewed. A single myth can sit in multiple themes by design, so growth is mostly absorbed without restructuring. Mitigation: theme tags are required fields on every new entry; weekly CI fails if any entry lacks at least one theme; dashboards expose theme size imbalances.

Risk · legal pressure

Frivolous defamation / "lawfare" attempts.

Every claim is tied to a primary source, served verbatim. The architecture is unusually defensible: nothing is generated on the fly, no paraphrase can be challenged as misattribution, and every legal-sensitive answer (apartheid / genocide / war crimes) is approved by editorial before deployment. The classifier produces a 4-letter label, not prose; it cannot misquote anyone.

Risk · platform deplatforming

Hosting, payments, or app-store removal.

Corpus mirrored on IPFS + GitHub. The catalog is a bundle of static JSON — replicable on any host in minutes. The classifier endpoint is the only piece that needs compute, and it's portable across providers (Option D removes proprietary-model dependency entirely). No payment dependency in the consumer flow.

Roadmap · v0.4

Voice + Telegram bot.

The same classifier-and-retrieval pipeline behind a STT/TTS layer for accessibility, plus a Telegram/WhatsApp surface (via Option C-style infra) for regional distribution where web reach is constrained. Both ride the same corpus and respect the verbatim-output discipline.

Roadmap · v0.5

Multilingual.

Arabic, French, Spanish, German next. The browse lane is trivial to translate (replace the strings in the JSONL); the classifier needs prompt-level translation or a multilingual model variant. Embeddings move to bge-m3 (already supports 100+ languages). Editorial team grows accordingly.

Roadmap · v0.6

Source provenance graph.

For each myth, render the network of sources cited and how they cite each other. Lets users see at a glance that a claim isn't propped up by a single op-ed but by overlapping UN, NGO, and academic work. Lives naturally in the browse lane — no model needed.

Roadmap · v1.0

Federated corpora.

Same engine, different corpora. The verbatim-retrieval architecture generalises to any closed-domain Q&A with a curated, sourced answer set — climate denial, vaccine disinformation, historical revisionism. The themes file and the canned-response templates are the only per-corpus artefacts that need custom work.
